# Research Protocol

# Research Principle

> The purpose of these experiments is not to demonstrate that the proposed method works.
>
> The purpose is to determine whether it works.
>
> Every experiment must be capable of disproving the current hypothesis.
>
> Negative results are acceptable.
>
> Baselines may outperform the proposed method.
>
> Real-world data may contradict simulated results.
>
> Hyperparameters may invalidate existing assumptions.
>
> Claims of novelty or superiority will only be made if supported by the experimental evidence.
>
> The integrity of the evaluation protocol is more important than the outcome of the experiments.

This paragraph is the first thing in this directory on purpose, and it is not decoration. If
everything else in this document is forgotten, this is the part that should still be true.

## What Phase 1 is

Phase 1's objective is **not** to prove that the hierarchical matchup engine
(`blendWithPrior`/`hierarchicalBlend` in `backend/src/utils/statUtils.js`, `getMatchupPlan`/
`getLiveMatchupPlan` in `backend/src/services/tendencyAnalytics.js`) is good. It is to build a
scientifically defensible evaluation framework capable of determining whether it is - one that
would produce a negative result cleanly and legibly if that's what the evidence supports, not one
built in a way that can only ever confirm what was already believed going in.

See `documentation/research-readiness-audit.md` for how this program got here: the central,
load-bearing finding of that audit is that the dataset currently in the product database (almost
entirely generated by `backend/src/scripts/matchSimulator.js`) has no real matchup-dependent
structure for the algorithm to be evaluated against - `matchSimulator.js` assigns dismissal
probability via `Math.random() < 0.045`, independent of batter, bowler, line, or length. Nothing
in Phase 1 evaluates the product's live data. Phase 1 evaluates the algorithm against data built
specifically to have known, controlled structure - see `dataset-assumptions.md`.

## The falsifiability invariant

Every major methodological decision in this program must be able to answer, explicitly and in
writing: **what evidence would convince us this choice is wrong?**

If the honest answer is "there is no result that would make us reject it," the decision is not a
scientific hypothesis - it's an implementation preference, and it should be labeled as one, not
dressed up as something it isn't. This applies to metric choice, hyperparameter values, the
existence of the live adjustment, the archetype boundaries, the prediction target itself -
everything. Each design document in this directory states this explicitly for the decisions it
makes, not as a formality but as the actual test each decision has to pass before it's used.

## Synthetic and real validation are never mixed

Per explicit instruction: synthetic-but-structured validation (Track A - does the estimator
recover a *known* ground-truth probability under controlled sparsity, using data built for this
program) and real-world validation (Track B - does it hold up on actual pilot matches, once they
exist) are two separate tracks, kept separate in code, in data, and in every document and result
this directory produces. A result from one is never presented as evidence for the other. Track B
cannot start until real pilot data exists; see `documentation/going-legal-and-live.md` for where
that stands.

## Directory layout

Proposed only as far as what Phase 1 actually needs - not the full eventual structure sketched
earlier, most of which (real datasets, real results across multiple pilot seasons, published
figures) doesn't exist yet and shouldn't be scaffolded before there's real content for it.

```
research/
  protocol.md                    - this file
  prediction-target.md           - what, precisely, is being predicted and why
  dataset-assumptions.md         - Track A (synthetic) vs Track B (real) explicitly separated
  synthetic/
    generator.js                 - the structured synthetic data-generating process
    generator.test.js            - verifies the generator actually produces the structure it claims to
  baselines.js                   - every baseline, computed from the same underlying queries
                                    getMatchupPlan uses (getLineLengthBreakdown,
                                    getPlayerIdsByArchetype - both already exported, zero changes
                                    to production code)
  harness/
    evaluate.js                  - the evaluation harness: seeds a real (in-memory) MongoDB,
                                    calls the real getMatchupPlan/getLiveMatchupPlan, enforces
                                    match-level + within-match temporal ordering
  metrics.js                     - Brier score, calibration, ranking, sample-efficiency, oracle
                                    comparison (Track A only)
  results/                       - raw experiment output, one subdirectory per run, each
                                    recording dataset version, split, seed, hyperparameters, code
                                    version, and metrics - created when the first experiment
                                    actually runs, not before
```

## Sequencing

Each step below is its own commit, in order. No step's code is written under the assumption that
a later step will "obviously" pass - each one is checked before moving to the next.

1. This document (`research: add protocol and evaluation policy`).
2. `prediction-target.md` (`research: define prediction target`).
3. `dataset-assumptions.md` (`research: document dataset assumptions`).
4. `synthetic/generator.js` + its own verification test (`research: implement structured
   synthetic generator`).
5. `baselines.js` (`research: add baseline framework`).
6. `harness/evaluate.js` (`research: add evaluation harness`).
7. `metrics.js` (`research: add calibration metrics`).
8. The first controlled experiment, run for real, results reported raw
   (`research: first controlled experiment`) - per explicit instruction, results come back for
   joint interpretation before any conclusion is written down anywhere.
